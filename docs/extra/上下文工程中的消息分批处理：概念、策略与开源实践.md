# 上下文工程中的消息分批处理：概念、策略与开源社区实践

> 一份面向广大技术读者的综述。力求「听得懂、跟得上、查得到」：专业名词都配有通俗解释，关键结论尽量标注出处。
> 整理时间：2026 年 11 月。

---

## 一、先搞清楚两个基本概念

### 1.1 什么是上下文工程（Context Engineering）

大语言模型（LLM）本身没有记忆：每一次调用，你发给它的全部内容——系统提示词、历史对话、检索到的资料、工具返回结果——就是它的「全部世界」。**上下文工程**就是「在每一次调用模型之前，决定往这个『世界』里放什么、不放什么、以什么顺序放」的学问。

一个直观的类比：上下文窗口（Context Window）是模型的「办公桌桌面」，面积有限。上下文工程就是不断收拾这张桌子的艺术——把常用的放手边，把不常用的进抽屉（外部存储），把过期的扔掉（裁剪/遗忘），把一大摞文件先压成摘要（压缩）再摆上桌面。

学术界近期的一份综述（*From Long Context to Selective Memory: A Survey of Memory-Centric Compression for Large Language Models*, arXiv:2610.21165）把这条主线概括为：长上下文 → 选择性记忆，核心问题是「信息在模型内部状态和外部存储之间如何流转」。

### 1.2 什么是「消息分批处理」（Message Batching）

「消息分批处理」并不是某一篇论文里的标准术语，而是工程实践中对一大类做法的统称：**不把全部消息一股脑塞进模型，而是按某种策略把消息分组、分批、分优先级地送进上下文窗口**。它大致落在四个层面上，本报告会逐一展开：

| 层面 | 关心的问题 | 典型代表 |
|---|---|---|
| ① 对话消息管理层 | 历史消息太多，窗口放不下，怎么办？ | LangChain、LlamaIndex、MemGPT/Letta、AutoGen |
| ② 内容压缩层 | 每条消息都很长，能不能先「瘦身」再进窗口？ | LLMLingua、分块（Chunking）、检索（RAG） |
| ③ 服务/API 层 | 很多请求都不着急，能不能攒一批一起算，便宜点？ | OpenAI Batch API、Anthropic Message Batches |
| ④ 推理引擎层 | GPU 一次能算很多条，怎么排班最划算？ | vLLM、SGLang、TensorRT-LLM、TGI |

> 一句话区分：①②是「一条对话内部怎么省地方」，③是「很多请求之间怎么省钱的排队策略」，④是「服务器底层怎么提高吞吐的调度算法」。四者经常叠加使用。

## 二、专业术语速查表

| 术语 | 英文/缩写 | 通俗解释 |
|---|---|---|
| 上下文窗口 | Context Window | 模型一次能「看到」的最大文本长度（按 token 计），超出部分会被直接丢弃或报错。 |
| Token（词元） | Token | 模型处理文本的最小单位，约等于 0.5~1 个英文单词或 0.5~1 个汉字。计费和长度限制都按 token 算。 |
| 词元化 | Tokenization | 把原始文本切成 token 的过程。 |
| 滑动窗口 | Sliding Window | 只保留最近 N 条（或最近 N 个 token）消息，更老的直接丢弃。类似手机的「只显示最近 100 条聊天记录」。 |
| 摘要缓冲 | Summary Buffer | 老消息不直接扔，而是先用模型压缩成一段摘要，摘要+近期原文一起放进上下文。 |
| 消息裁剪 | Message Trimming | 在发送给模型前，按 token 预算精确删掉一部分消息，通常优先保留系统提示词和最近的消息。 |
| KV 缓存 | KV Cache | 模型在生成过程中保存的中间计算结果（每个 token 对应的 Key/Value 向量）。复用它可以避免重复计算，但非常占显存。 |
| 分页注意力 | PagedAttention | vLLM 提出的显存管理技术：把 KV 缓存切成固定大小的「页」，像操作系统管理内存分页一样按需分配，把显存浪费压到 4% 以下。 |
| 连续批处理 | Continuous Batching | 推理引擎的调度技术：不按「整批请求」排队，而是每生成一个 token 就重新排一次队——完成的请求立刻下车，新请求立刻上车。 |
| 迭代级调度 | Iteration-level Scheduling | 连续批处理的学术名称，最早由 Orca 系统（OSDI 2022）提出。 |
| Prefill / Decode | 预填充 / 解码 | 一次推理的两个阶段：Prefill 把输入提示词全部「读进去」（吃算力），Decode 逐个生成输出 token（吃显存带宽）。 |
| 前缀缓存 | Prefix Caching | 多个请求如果开头部分相同（如相同的系统提示词），这部分的 KV 缓存可以共享复用，不用重算。 |
| 提示词缓存 | Prompt Caching | API 层面的缓存：把不变的长前缀标记出来，服务商对「缓存命中」的输入收更低价格。 |
| 检索增强生成 | RAG | 先从外部知识库检索相关内容，再塞进提示词让模型回答；相当于「开卷考试」。 |
| 记忆分层 | Memory Tiering | 把记忆分成「主上下文 / 短期 / 长期 / 归档」多层，按需搬运。MemGPT 是代表。 |
| 上下文压缩 | Context Compression | 在信息进入模型前减少 token 数量的所有技术的总称（摘要、删 token、检索筛选等）。 |
| 困惑度 | Perplexity | 衡量「语言模型对一段文本有多惊讶」的指标。LLMLingua 利用它判断哪些 token 信息量低、可以删。 |
| 离线批处理 | Offline / Async Batching | 把大量请求打包成一个文件异步提交，接受最长 24 小时的延迟，换取约五折的价格。 |
| 实时性 SLA | Service-Level Agreement | 服务等级协议，比如「24 小时内一定算完」。 |

## 三、为什么需要消息分批处理：四个真实痛点

1. **窗口装不下。** 对话越长，历史消息越多，总有一天会顶到上下文窗口上限；顶到之后，要么报错，要么最早的对话被静默截断——用户上周告诉机器人的偏好就此「失忆」。
2. **装得下但太贵。** 计费按 token 算。每次都把几万 token 的历史重发一遍，账单会线性增长。
3. **装得下但变慢。** 输入越长，Prefill 阶段越慢，首 token 延迟（TTFT）越高；长上下文还会稀释模型注意力，造成「迷失在中间」（Lost in the Middle）现象——模型对上下文中间部分的信息利用率显著低于开头和结尾。
4. **GPU 利用率低。** 如果每次只处理一条请求，显卡大部分时间闲着；但简单地把多条请求捆成一批（静态批处理）又会被最长的那条拖住。

消息分批处理就是在这四个痛点上长出来的全套工具箱。

## 四、层面 ①：对话消息管理层——「桌子满了怎么收拾」

这是普通开发者最常打交道的层面。核心策略可以归纳为一个谱系：**从「硬丢弃」到「软压缩」再到「智能搬运」**。

### 4.1 策略一：滑动窗口（Sliding Window）——最简单的「只留最近」

**做法**：只保留最近 k 轮对话，其余直接丢弃。

**出处与实现**：
- LangChain 提供 `ConversationBufferWindowMemory(k=3)`，只保留最近 3 轮；也提供更精确的 `trim_messages(max_tokens=…, strategy="last")`，按 token 预算从头部裁剪，同时允许保留系统提示词、保证消息以人类消息开头等细节（见 LangChain 官方文档与社区实战文章 [LangChain 上下文工程之聊天记录压缩](https://www.cnblogs.com/zhanchenjin/p/21347016)）。
- AutoGen 社区文档同样建议：长对话中给消息列表加一个只留最近 N 条的 buffer，交接给其他 agent 时也只传摘要或选中的消息（见 [AutoGen Conversation Patterns](https://agentdevpro.com/frameworks/autogen/conversation-patterns/)）。

**优点**：实现一行代码，确定性强。
**缺点**：丢掉的信息彻底丢失，「我上周说过我叫张三」这类事实保不住。

### 4.2 策略二：摘要缓冲（Summary Buffer）——「老消息先压成便签」

**做法**：设定一个 token 预算；当历史超过预算时，把最老的消息迭代式地总结成一段摘要，摘要+近期原文一起进入下一轮上下文。

**出处与实现**：
- LangChain 的 `ConversationSummaryBufferMemory(max_token_limit=500)` 是典型实现（出处同上）。
- LlamaIndex 的 `ChatSummaryMemoryBuffer`：超出 `token_limit` 的历史会被逐段总结为单条消息。官方示例显示，超限时整条历史被压缩为一段 system 消息摘要，并随新对话持续更新（见 [LlamaIndex 官方示例](https://developers.llamaindex.ai/python/examples/memory/chatsummarymemorybuffer/)）。
- Anthropic API 在平台层提供了类似的 **Compaction**（压缩）能力：对话接近窗口上限时，服务端把早期历史浓缩为摘要，使会话得以继续（beta 特性，见 [Anthropic Prompt Caching 与上下文工程指南](https://hidekazu-konishi.com/entry/anthropic_claude_api_prompt_caching_and_token_efficiency.html) 第 7.3 节）。

**优点**：不丢「语义」，老信息以低成本形式保留。
**缺点**：摘要有损——细节、精确数字、原始措辞会丢；且摘要本身也占 token，需要设好上限（社区经验是不建议压过头，否则回答质量下降、重试成本反而更高）。

### 4.3 策略三：Flush 机制——「桌面的东西按批倒进抽屉，抽屉里再分拣」

**做法**：短期记忆设一个阈值（如 token 预算的 70%），一旦超出，就把最老的一批消息（按固定批次大小，如 3000 token）**成批 flush（冲刷）到长期记忆**，由不同的「记忆块」分别处理：有的提取事实、有的存进向量库、有的永久保留核心信息。

**出处与实现**：
- LlamaIndex 新一代 `Memory` 类是代表：短期记忆是一个 FIFO 队列；超出 `chat_history_token_ratio`（默认 0.7）后，最老的消息按 `token_flush_size`（默认 3000）成批送入各类 **Memory Block**（记忆块）——静态核心信息块、LLM 事实提取块、向量记忆块等；检索时短期+长期合并，超限时按各块的 `priority` 优先级截断。这实际上是「消息分批处理」四个字最字面的实现：**消息按批流动于短期与长期记忆之间**（见 [LlamaIndex 官方 Memory 文档](https://llamaindex.openml.io/python/framework/module_guides/deploying/agents/memory/)）。

**优点**：滚动进行、延迟平滑；长期记忆可以按语义检索，不依赖「最近」这个单一维度。
**缺点**：架构复杂度高；检索质量取决于嵌入模型与块设计。

### 4.4 策略四：虚拟上下文与分页（MemGPT / Letta）——「让模型自己收拾桌子」

**做法**：借鉴操作系统的虚拟内存思想。上下文窗口是「内存」，外部存储是「磁盘」；当窗口快满时，由**模型自己通过函数调用**把不重要的内容「换出」到外部存储、需要时再「换入」。系统用中断（interrupt）机制在模型和用户之间调度控制权。

**出处**：MemGPT 论文（*MemGPT: Towards LLMs as Operating Systems*, arXiv:2310.08560，UC Berkeley，2023）。它把记忆分为三层：
1. **主上下文（Main Context）**：提示词本身，唯一模型直接可见的层；
2. **召回存储（Recall Storage）**：完整对话历史数据库，被换出的消息进这里，按需分页查询取回；
3. **归档存储（Archival Storage）**：任意长度的文本对象库（论文实现为 PostgreSQL + pgvector 向量库），存放事实、文档。

论文实验中，深记忆检索（Deep Memory Retrieval）准确率从 32.1% 提升到 92.5%。原仓库已归档，后续发展为开源框架 **Letta**（出处：[MemGPT 架构解析](https://aimemoryworks.com/architecture/virtual-context-memgpt/)、[awesome-agent-memory 存档笔记](https://github.com/Snseam/awesome-agent-memory/blob/main/products/archives/memgpt-overview.md)、[MemX 词条](https://memx.app/glossary/memgpt/)）。

**优点**：上下文「理论上无限」；搬运决策由最了解语义的人——模型自己——做出。
**缺点**：每次搬运都是一次工具调用，会消耗 token 和轮次；社区实践反馈「给了 agent 最大的控制权，也给了它最多浪费 token 的方式」。适合超长会话，不太适合短平快任务。

### 4.5 学术视角：Select–Compress–Store–Recover 流水线

2026 年的综述（*From Long Context to Selective Memory*，arXiv:2610.21165）将上述应用层做法统一为一个四步流水线：**选择（Select）→ 压缩（Compress）→ 存储（Store）→ 恢复（Recover）**，并把「学习式压缩控制」形式化为「任务收益 − 成本」的优化问题。另有面向流式场景的综述（arXiv:2603.04592）把重点放在**在线、实时约束下的动态预算分配**——也就是「分批」必须跟着延迟预算走。eBay 2026 年的工作（arXiv:2603.29193）给出了一个自适应压缩框架：按「相关性 + 时效性 + 依赖性」打分排序历史消息，再结合「连贯性感知」筛选与动态预算分配，在 LOCOMO / LOCCO / LongBench 基准上同时改善了回答质量与 token 效率。

> **小结（层面①）**：谱系从硬到软——滑动窗口（丢）→ 摘要缓冲（压）→ Flush + 记忆块（搬）→ MemGPT 分页（模型自己搬）。工程上最常见的是「滑动窗口 + 摘要」组合拳，长会话系统越来越多采用「Flush + 分层记忆」。

## 五、层面 ②：内容压缩层——「每条消息先瘦身再上桌」

消息管理层管的是「哪几条进窗口」，压缩层管的是「每条怎么变短」。

### 5.1 提示词压缩：LLMLingua 家族

**做法**：用一个**小模型**（如 GPT2-small、LLaMA-7B）先读一遍提示词，计算每个 token 的困惑度（perplexity，模型对这段文本的「惊讶程度」），把「不太惊讶」的、信息量低的 token 删掉，只把高信息量的内容送进大模型。配合**预算控制器**（Budget Controller）对不同部分（指令、示例、问题）分配不同的压缩率。

**出处与数据**（微软研究院，EMNLP 2023 / ACL 2024）：
- **LLMLingua**：最高 20 倍压缩，性能损失很小；在数学推理（GSM8K）上 20 倍压缩后甚至仍优于简单提示词（出处：[PromptHub 论文解读](https://www.prompthub.us/blog/compressing-prompts-with-llmlingua-reduce-costs-retain-performance)、[EveryDev 工具页](https://www.everydev.ai/tools/llmlingua)）。
- **LongLLMLingua**（ACL 2024）：针对「迷失在中间」问题做问题感知压缩与文档重排，只用 1/4 的 token 使 RAG 性能提升最高 21.4%。
- **LLMLingua-2**：用从 GPT-4 蒸馏的 token 分类器替换打分模型，速度快 3~6 倍，任务无关。
- 开源协议 MIT，提供与 LangChain、LlamaIndex、Prompt Flow 的集成（出处：[Caveman 对比页](https://caveman.so/compare/llmlingua)、[GitHub microsoft/LLMLingua](https://github.com/microsoft/LLMLingua)）。

**注意**：工具定义 / 函数 schema 等结构化内容不能压缩，否则会破坏格式（出处：[LLMLingua 教程](https://itsourcecode.com/web-dev/prompt-compression-llmlingua-tutorial/)）。

### 5.2 其他通用技术

分块（Chunking，把长文本切成逻辑小块，可顺序或并行处理，配合重叠窗口保持连贯）、检索筛选（RAG，只把相关段落放进提示词）、去冗余、元数据标注等，见综合技术清单（出处：[Context compression techniques](https://palospublishing.com/context-compression-techniques-for-longer-llm-prompts/)）。长上下文技术的总体分类学（位置外推、注意力近似、提示压缩、滑窗分段等）见 IJCAI 2024 综述（出处：[A Survey of Techniques to Extend the Context Length](https://ijcai.org/proceedings/2024/0917.pdf)）。

## 六、层面 ③：服务/API 层——「不着急的请求攒一批，打五折」

**做法**：把成百上千个请求打包成一个文件（JSONL），一次性提交，平台异步处理，承诺 **24 小时内完成**，价格约为同步 API 的 **五折**，且使用**独立的限流额度池**（不影响在线业务）。

**出处与数据**：
- **OpenAI Batch API**：输入输出 token 均 5 折；单批最多 50,000 个请求、文件 200MB；适用场景：跑评测、大数据集分类、embedding 生成、离线生成（出处：[OpenAI 官方 Batch API 指南](https://developers.openai.com/api/docs/guides/batch)、[Batch API FAQ](https://help.openai.com/en/articles/9197833-batch-api-faq)）。
- **Anthropic Message Batches**：同样 5 折，单批最多 10,000 个请求，官方称多数批次 1 小时内完成；折扣可与 Prompt Caching 叠加（出处：[NeuralTrust 批处理对比](https://neuraltrust.ai/blog/llm-batching-async-inference)）。
- 组合技巧：批内请求共享同一系统提示词时，提示词缓存会在批内生效，**五折之上再叠缓存折扣**，输入 token 实际约为原价的 42.5%（出处：[ssimplifi 分析](https://ssimplifi.com/blog/batch-api-vs-real-time-openai)）。

**适用 / 不适用**：适合分类、标注、评测、离线摘要等「没有人在等答案」的任务；不适合实时对话、安全风控等场景。**结果按 `custom_id` 匹配，不能按顺序对号**（出处：[Anthropic 指南](https://hidekazu-konishi.com/entry/anthropic_claude_api_prompt_caching_and_token_efficiency.html) 第 11 节）。

## 七、层面 ④：推理引擎层——「GPU 排班的学问」

这一层离普通应用最远，但决定了「批处理」这个词在系统领域的原始含义：**同一个模型，一次前向计算同时服务多条请求**。

### 7.1 从静态批到连续批处理（Continuous Batching）

**问题**：静态批处理把 N 个请求捆在一起跑，必须等最长的那条生成完才整批释放——短请求早早完成，GPU 却在陪跑，实测可能浪费 30~70% 的时间。

**做法（迭代级调度）**：调度单位从「请求」降为「迭代（iteration，即一次 token 生成）」。每跑完一步：已完成的请求立刻下车并返回结果，队列中的新请求立刻上车（先补 Prefill，再一起 Decode）。

**出处**：Orca 系统（*Orca: A Distributed Serving System for Transformer-Based Generative Models*, Yu et al., **OSDI 2022**）首次提出 iteration-level scheduling 与 selective batching，在 GPT-3 175B 上报告了相对 FasterTransformer 最高 **36.9×** 的吞吐提升（出处：[Morph 连续批处理解析](https://www.morphllm.com/continuous-batching)、[Sesen 溯源](https://sesen.ai/blog/llm-serving-continuous-batching-paged-attention)）。

### 7.2 PagedAttention 与 vLLM

**做法**：把 KV 缓存切成固定大小的块（block，通常 16 个 token），用「块表」映射逻辑位置到物理块，像操作系统分页一样按需分配、用完即还、还支持块级共享（前缀缓存）。传统连续分配会因碎片和过度预留浪费 60~80% 的 KV 显存，PagedAttention 把浪费压到 **4% 以下**。

**出处**：vLLM（*Efficient Memory Management for Large Language Model Serving with PagedAttention*, Kwon et al., **SOSP 2023**）。两者结合后，在 ShareGPT 负载、LLaMA-13B、A100 上相对 HuggingFace Transformers 吞吐提升约 **14~24×**，相对 FasterTransformer/TGI 提升约 **2.2~3.5×**（出处：[掘金技术解析](https://juejin.cn/post/7671081747917488171)、[RunPod 指南](https://www.runpod.io/articles/guides/vllm-pagedattention-continuous-batching)、[datasops 实测讨论](https://www.datasops.com/blog/vllm-inference-server)）。

### 7.3 各家引擎的同一种语言

这项技术在各开源/商用引擎中名字不同、机制相同——**每一轮重新决定批里有谁**：

| 引擎 | 名称 | 备注 |
|---|---|---|
| vLLM | Continuous Batching | 与 PagedAttention 配套，开源默认选择 |
| NVIDIA TensorRT-LLM | In-flight Batching | Batch Manager 组件逐迭代进出 |
| Hugging Face TGI | Continuous Batching | Rust 路由器缓冲请求 |
| SGLang | Continuous Batching | 配 RadixAttention 前缀树共享 |
| Orca（学术） | Iteration-level Scheduling | 2022 年原始设计 |

（出处：[Morph 对照表](https://www.morphllm.com/continuous-batching)、[vLLM internals 课程](https://github.com/Firojpaudel/vLLM_internals)）

### 7.4 衍生调度技术

- **Chunked Prefill（分块预填充）**：新请求的长提示词切块，与老请求的 Decode 交错进行，避免长 Prefill 阻塞短 Decode。
- **Prefix Caching（前缀缓存）**：共享前缀（系统提示词、RAG 公共上下文）的 KV 块直接复用，RAG/多轮对话负载收益最大（出处：[preporato 实验](https://preporato.com/labs/vllm-serving)）。
- **Prefill/Decode 分离**（DistServe、Mooncake）：把两个阶段拆到不同机器，各配各的硬件（出处：[systemdesigntutorial 梳理](https://systemdesigntutorial.com/m65-inference-serving.html)）。

## 九、给读者的实践建议

1. **先量体裁衣，再选策略**。消息少于几十轮：直接用框架自带的滑动窗口即可；长会话客服/陪伴：上「摘要缓冲 + 向量长期记忆」；超长文档分析或多月会话：考虑 MemGPT/Letta 式分页。
2. **摘要和缓存是好搭档**。把「稳定的系统提示词」放最前并开 Prompt Caching，把「会增长的历史」放后面——缓存命中能对冲摘要带来的重算成本（出处：[Anthropic 指南](https://hidekazu-konishi.com/entry/anthropic_claude_api_prompt_caching_and_token_efficiency.html) §4、§10）。
3. **离线任务一律先问「能不能走 Batch API」**。没有人在等的流量，走批处理等于直接打五折，还不占在线限流额度。
4. **自部署推理直接选支持连续批处理的引擎**（vLLM/SGLang 等），别自己造静态批处理的轮子。
5. **压缩要留验证**。社区共识是「过度压缩省下的 token，会被质量下降带来的重试吃回去」；任何激进的上下文变更都应在真实流量上评测后再上线。
6. **注意 token 计量工具链**：不同模型分词器不同，用错 tokenizer 会让预算和限流判断全线失真（出处：同指南 §11）。

## 十、局限与未来方向

- **压缩损失难以完全避免**：摘要漂移、细节丢失仍是开放问题；2026 年的自适应压缩工作（如 arXiv:2603.29193 的连贯性感知筛选）在尝试把「该删什么」变成可学习的决策。
- **评测基准正在成熟**：LOCOMO（长期记忆）、LOCCO（一致性）、LongBench（长上下文推理）逐渐成为标准考题。
- **从「静态省资源」走向「动态预算分配」**：流式 LLM 综述（arXiv:2603.04592）指出的方向是——在实时延迟约束下，在线决定每批消息「放多少、放哪些」。
- **KV 压缩与外部记忆的合流**：内存中心化压缩综述（arXiv:2610.21165）认为，模型内部缓存管理与外部记忆检索将在统一成本模型下被一起优化。
