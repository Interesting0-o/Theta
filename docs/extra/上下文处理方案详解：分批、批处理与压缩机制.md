# 上下文处理方案详解：分批、批处理与压缩机制

> 本文是《上下文工程中的消息分批处理：概念、策略与开源实践》的姊妹篇，聚焦**工程实现**：
> ① 最小单位怎么划定；② 怎么分批；③ 对一批消息能做哪些处理；④ 这些处理最终如何落实为「压缩内容」。

## 〇、总览：一条标准处理管线

任何上下文处理系统，无论开源还是自研，都可以拆解为同一条五级管线：

```
原始消息流
   │
   ▼
[1] 划定最小单位（Unitize）   ← 决定「什么东西不可拆」
   │
   ▼
[2] 分批（Batch）            ← 决定「多少单位算一批、按什么维度切」
   │   每个批附带元数据：batch_id / 时间范围 / token 数 / 话题 / 重要性分
   ▼
[3] 批级处理（Process）       ← 对每一批执行一个算子：保留/丢弃/摘要/抽取/向量化/引用……
   │
   ▼
[4] 重装配（Reassemble）      ← 处理产物（摘要消息、事实条目、指针）+ 未处理的近期原文 → 新上下文
   │
   ▼
[5] 预算校验（Budget Check）  ← 总 token 是否超预算？超了回到 [2]，对更靠前的批再压一级
   │
   ▼
发给模型
```

整条管线由**预算控制器（Budget Controller）**驱动：它设定总预算、各部分配额、触发阈值。LLMLingua 论文中首次把「对不同部分分配不同压缩率」显式做成预算控制器，这个思想可以原样搬到消息管理层（出处：[LLMLingua, EMNLP 2023](https://github.com/microsoft/LLMLingua)）。

## 一、第一步：最小单位怎么划定

最小单位（atomic unit）的选择决定了后面所有策略的粒度。**划定原则只有一条：语义上不可分割的东西必须绑在一起。**

### 1.1 候选粒度对比

| 粒度 | 定义 | 优点 | 致命缺点 |
|---|---|---|---|
| Token 级 | 单个词元 | 最精细，压缩率上限最高 | 破坏语法结构，无法承载「删除」这一决策（模型不知道删了哪里） |
| 消息级 | 一条 role + content | 实现最简单 | 误拆**工具调用组**（见 1.2） |
| **工具调用组** ⭐ | assistant 消息 + 其发起的全部 tool 消息 | 语义原子，AI 发起的动作闭环完整 | 组内仍可能很长（如大段代码执行结果） |
| 轮次级 | 一问一答（user+assistant 对） | 符合人类对话直觉 | 一轮里可能夹多组工具调用，粒度偏粗 |
| 话题段 | 语义聚类出的连续片段 | 压缩/搬运时语义最完整 | 需要 embedding/聚类，延迟与成本更高 |

### 1.2 为什么「AI 消息 + 它的 tool 消息」必须绑定

现代工具调用（Function Calling）协议下，一次典型的智能体动作长这样：

```jsonc
{ "role": "assistant", "tool_calls": [
    {"id": "call_1", "function": {"name": "search", "arguments": "{\"q\":\"...\"}"}} ] }
{ "role": "tool", "tool_call_id": "call_1", "content": "<搜索结果，可能几千 token>" }
```

两条消息是**同一次动作的请求与回执**。如果只保留 assistant 消息而删掉 tool 结果，模型会看到「自己调用了一个工具，然后……没有任何返回」——轻则困惑、重则输出幻觉；反过来只留结果删掉调用，结果成了无源之水。更麻烦的是很多 API 会**直接报格式错误**（assistant 带 tool_calls 的消息后必须紧跟对应 tool 消息）。

**结论：工具调用组是最小原子单位。** 用户提出的两种直觉（「一条消息一个单位」「AI 消息+tool 消息一个单位」）中，后者是正确的工程选择；前者只适用于不带工具调用的纯对话场景。

LlamaIndex 的 flush 机制实际上就是这么做的——它按批搬运的是结构完整的对话单元，而不是裸文本片段（出处：[LlamaIndex Memory 文档](https://llamaindex.openml.io/python/framework/module_guides/deploying/agents/memory/)）。

### 1.3 原子单位规则清单（可直接照抄的约束）

```
R1  system 消息永远不参与分批，永远完整保留在最前。
R2  工具调用组 = assistant(tool_calls) + 其引用的全部 tool 消息，同生同死。
R3  单位边界不跨越「轮」：一个 user 消息开启新单位。
R4  单位内部的 tool 消息过多时（如 >5 条），允许组内二次切分，
    但必须保留 组头(assistant) + 第一条结果 作为「组的代表」。
R5  被压缩后的单位在上下文中的替代物（摘要/指针）仍算一个单位，
    保证重装配后结构合法。
```

R4 对应一个真实需求：agent 批量调几十个工具时，单个工具调用组可能比整个预算还大。此时组内按 tool 消息切小批，组头降级为「执行了 N 个工具，结果如下」。

## 二、第二步：怎么分批

### 2.1 五种切批维度（可叠加）

| 维度 | 规则 | 适用场景 | 代表实现 |
|---|---|---|---|
| 时间批 | 最近 T 分钟/小时的消息为一批 | 客服、陪伴类连续会话 | 通用 |
| 数量批 | 每 k 个单位一批 | 批处理均匀、延迟低 | LangChain 窗口记忆 `k=3` |
| **Token 批** ⭐ | 每批不超过 B 个 token（如 3000） | **最常用**，压缩对象大小可控 | LlamaIndex `token_flush_size=3000` |
| 语义批 | embedding 聚类，同话题归一批 | 摘要质量最高（一批=一个主题） | 自研/Graphiti 的 episode 概念 |
| 优先级批 | 按重要度分（核心事实>任务状态>闲聊） | 多级记忆系统 | LlamaIndex Memory Block 的 `priority` |

工程上最稳的组合是 **Token 批为主干 + 语义批兜底**：先按 token 预算切，若切点恰好把同一话题劈成两半，就把边界挪到话题结束处（允许该批超出预算 10~20%）。

### 2.2 批的元数据设计

每个批必须带齐五类元数据，后续所有算子都依赖它们：

```jsonc
{
  "batch_id": "b_017",
  "span":      {"unit_from": 12, "unit_to": 15},   // 覆盖哪些单位
  "tokens":    2840,
  "time_range":["2026-11-03T10:12:00", "2026-11-03T10:31:00"],
  "topic_hint":"用户确认报表口径",                   // 语义批/LLM 标注
  "importance": 0.62                               // 0~1，由评分器给出
}
```

`importance` 的打分可以逐步升级：v1 用启发式（含数字/日期/用户偏好关键词加分，寒暄减分）；v2 用小模型打分；v3 用注意力统计（见 4.3 的 H2O 思想）。

### 2.3 分批的触发时机

- **阈值触发（主流）**：历史区 token 数超过预算的 70%（LlamaIndex 的 `chat_history_token_ratio` 默认值）时，把最老的一批移出。优点：只在需要时花钱。
- **周期性触发**：每 N 轮强制处理一次。优点：摘要上下文连贯、单次处理量大更省；缺点：有突发成本。
- **事件触发**：检测到话题切换、任务完成、用户显式说「记住这个」时立即处理该批。Zep/Graphiti 的 episode（情节）概念就是这种思路——把事件序列当作有意义的整体来抽取事实（出处：[Zylos 对 Graphiti 的分析](https://zylos.ai/en/research/2026-04-20-memory-consolidation-ai-agents/)）。

## 三、第三步：对一批消息能做哪些处理（算子全集）

把开源社区的所有做法归纳一下，批级算子一共九种，可归为四大类：

### 3.1 空间类算子（批还在上下文里，只是变小）

| 算子 | 做什么 | 信息损失 | 出处/代表 |
|---|---|---|---|
| **裁剪 Trim** | 按 token 预算从批内删尾部内容，常配合「保留前 m 条 tool 结果」 | 中（尾部丢失） | LangChain `trim_messages`（[实战](https://www.cnblogs.com/zhanchenjin/p/21347016)） |
| **删 token Compress** | 小模型按困惑度删低信息量 token，工具 schema 等结构不可压 | 低-中 | LLMLingua 家族（[GitHub](https://github.com/microsoft/LLMLingua)） |
| **占位降级 Replace** | 长内容换成占位符，如 `[工具结果 2840 tokens 已存档 #b_017]` | 无（可回取） | Anthropic Context Editing 的同类思想 |

### 3.2 语义类算子（批变成一段更短的「话」）

| 算子 | 做什么 | 信息损失 | 出处/代表 |
|---|---|---|---|
| **摘要 Summarize** | LLM 把一批压成一段摘要消息（生成式压缩） | 中-高（细节、措辞丢失） | `ConversationSummaryBufferMemory`、`ChatSummaryMemoryBuffer`、Anthropic Compaction |
| **抽取 Extract** | 不把批压成散文，而是抽出结构化事实/偏好/实体关系，写成记忆条目 | 低-中（只丢「氛围」） | Mem0：每批提取 facts 并去重，官方称最高省 80% token（[arXiv:2504.19413](https://zylos.ai/en/research/2026-04-20-memory-consolidation-ai-agents/)） |
| **提取模板 Fill** | 用固定模板从批里填槽（时间、对象、结论、数字） | 中（只有槽位内信息） | 自研，适合强结构化业务（订单、工单） |

### 3.3 搬运类算子（批离开上下文，进入外部存储）

| 算子 | 做什么 | 可恢复性 | 出处/代表 |
|---|---|---|---|
| **向量化 Embed** | 批原文进向量库，上下文里只留检索入口 | 完全可恢复 | 一切 RAG 式记忆 |
| **引用 Reference** | 上下文留「指针 + 一句话索引」，需要时 agent 主动取回 | 完全可恢复 | MemGPT 的召回存储分页（[架构解析](https://aimemoryworks.com/architecture/virtual-context-memgpt/)） |
| **归档 Archive** | 进冷存储（文件/数据库），仅审计用 | 可恢复但延迟高 | MemGPT 归档层 |

### 3.4 调度类算子（不改变批本身，改变批的次序与可见性）

| 算子 | 做什么 | 出处/代表 |
|---|---|---|
| **重排 Rerank** | 进入窗口前按与当前问题的相关性排序，重要的放两头（规避「迷失在中间」） | LongLLMLingua 的 question-aware reordering（[PromptHub](https://www.prompthub.us/blog/compressing-prompts-with-llmlingua-reduce-costs-retain-performance)） |
| **合并 Merge** | 相邻小批合并成一个处理单元，省算子调用次数 | 通用 |

### 3.5 算子选择决策树

```
这批消息……
├─ 近期且与当前任务直接相关 ──→ KEEP（原样保留）
├─ 含用户偏好/事实/承诺 ──────→ EXTRACT（抽成记忆条目）+ REFERENCE（留指针）
├─ 含工具结果等「用完即弃」内容 ─→ TRIM / REPLACE（降级占位）
├─ 话题完整、未来可能问起 ────→ SUMMARIZE（生成式压缩）或 EMBED（向量搬运）
├─ 闲聊/过渡/已失效 ─────────→ DROP
└─ 与当前问题相关但排在中间 ──→ RERANK 提位
```

## 四、核心章节：压缩内容到底怎么实现

所有批处理最终都收敛为三种基本动作：**删、缩、搬**。下面按「压缩发生的层次」从底到顶讲清楚每一种的实现机制。

### 4.1 层次 0：模型内部表征的压缩（KV Cache 级）

这一层不动文本，动的是模型推理时的中间缓存。它回答的问题是：「即使文本进了上下文，模型在算的时候能不能只认真看一部分？」

**机制 A：注意力沉没 + 滑窗（结构保留）**
MIT & Meta 的 StreamingLLM（ICLR 2024）发现一个反直觉现象：序列开头的几个 token（哪怕只是 `<BOS>`）会吸收异常高的注意力权重，称为**注意力沉没（Attention Sink）**；一旦把它们连同滑窗一起驱逐，Llama-2-13B 的困惑度从 5.4 暴涨到 5158。方案因此极简：**永远保留开头 4 个 token 的 KV + 最近一个窗口的 KV**，中间全部驱逐。无需微调即可稳定处理 400 万 token 以上的流（出处：[arXiv:2309.17453](https://arxiv.org/abs/2309.17453)、[中文拆解](https://pinghaoyang.com.cn/aigc/posts/streamingllm/)）。

**机制 B：重击者驱逐（动态评分保留）**
H2O（Heavy-Hitter Oracle, NeurIPS 2023）维护每个 token 的**累计注意力得分**，驱逐得分最低的非近期 token，只保留约 10% 的「重击者」token。实验证明注意力矩阵呈极端幂律稀疏，90% 的 filler token 驱逐后吞吐提升约 3 倍（出处：[arXiv:2306.14048](https://mbrenndoerfer.com/writing/kv-cache-compression-eviction-quantization-h2o-algorithm)、[Hyperstack 综述](https://www.hyperstack.cloud/technical-resources/tutorials/how-to-optimise-the-kv-cache-a-guide-to-faster-cheaper-llm-inference)）。

**机制 C：观测窗聚类（Prefill 前压缩）**
SnapKV 在 prefill 阶段用提示词尾部 32 个 token 作为「观测窗」，统计各历史位置收到的注意力投票，按注意力头聚类保留重要 token 簇，一次性压缩约 80~85% 的 KV，16% 的缓存即可保留 99.1% 的多跳检索准确率，解码提速 3.6 倍（出处：[arXiv:2404.14469](https://hsilvosa.com/research/kv-cache-eviction-snapkv/)、[Navokit 图解](https://www.navokit.com/en/blog/kv-cache-compression-streaming-llm-snapkv)）。

**机制 D：非均匀预算与量化**
PyramidKV 按「信息漏斗」给浅层多分缓存、深层少分；Ada-KV 按注意力头自适应分配；KIVI/KVQuant 对 KV 做 2~4 bit 量化，Key 按通道、Value 按 token（出处：[大模型笔记长上下文条目](https://zyxdtk.github.io/LLM-Note/4.text-model/LongContext/)、[算法对照](https://veloxquant-mlx.netlify.app/docs/algorithms/overview/)）。

> **给应用开发者的启示**：这三个机制的思想可以平移到消息管理层——「沉没 token ≈ 系统提示词永远保留」「重击者 ≈ 按累计重要性给消息打分」「观测窗 ≈ 用最近的提问去衡量历史消息的相关性」。eBay 的自适应压缩框架正是这么做的（arXiv:2603.29193）。

### 4.2 层次 1：Token 级压缩（提示词瘦身）

**实现**：小模型（GPT2-small / LLaMA-7B 级别）计算每个 token 的**困惑度**（模型对该 token 的惊讶程度），按预算控制器分配的部件配额（指令保真、示例可压、问题不可压）删低困惑度 token。LLMLingua 支持最高 20 倍压缩，GSM8K 上 20 倍压缩后甚至优于原始提示词；LLMLingua-2 用蒸馏出的 token 分类器替换逐 token 打分，速度提升 3~6 倍（出处：[GitHub microsoft/LLMLingua](https://github.com/microsoft/LLMLingua)、[PromptHub 解读](https://www.prompthub.us/blog/compressing-prompts-with-llmlingua-reduce-costs-retain-performance)）。

**边界**：函数 schema、JSON 结构、代码语法等高结构内容不可压，否则会破坏格式（[教程](https://itsourcecode.com/web-dev/prompt-compression-llmlingua-tutorial/)）。

### 4.3 层次 2：消息级压缩（删整条）

**实现**：最朴素也最常用——滑动窗口直接 DROP 最老的单位。成本为零、行为确定。改进版是**条件删除**：给每条消息算保留分（关键词命中 + 实体出现 + 时间近因），分数低于阈值才删，避免「用户三周前说的过敏史被滑窗误杀」。

### 4.4 层次 3：语义级压缩（一批 → 一段话）

这是「压缩」一词最常被指的东西，两种实现：

**生成式摘要（Abstractive）**：LLM 读一批，用自己的话重写为更短的摘要消息。
- 要点：摘要提示词里必须写明「保留具体数字、专名、承诺、未完成事项」；
- 迭代式压缩：新批的摘要要与旧摘要合并再压（LangChain `ConversationSummaryBufferMemory` 的做法），防止多层摘要后信息衰减成空话；
- 成本：摘要本身花 token，摘要上限要设死（经验：历史区摘要总量 ≤ 原历史的 15~20%）。

**事实抽取（Extractive-to-semantic）**：不生成散文，而是让 LLM 输出结构化条目，如 `{"type":"preference","content":"用户对账口径要求含税","source":"b_017","valid_from":"2026-11-03"}`。Mem0 是该范式的代表：写入时逐批提取事实、实体、关系，与既有记忆去重（ADD/UPDATE/NOOP 三分类），官方称比全量注入省约 80% token；Zep/Graphiti 更进一步给每条事实加**双时间戳**（录入时间 + 真实有效期），新事实与旧事实冲突时让旧事实「过期」而非删除，保留历史（出处：[Mem0 分析](https://zylos.ai/en/research/2026-04-20-memory-consolidation-ai-agents/)、[Graphiti 机制](https://atlan.com/know/episodic-memory-ai-agents/)）。

### 4.5 层次 4：检索级「压缩」（选择性载入，本质不压缩）

**实现**：原文完整存外部，每次请求只按相关性取 top-k。RAG 是这类；严格说它不是压缩而是**搬运 + 选择**。MemGPT 的召回存储把换出的消息分页存库，模型用函数调用按查询取回（Deep Memory Retrieval 准确率 32.1%→92.5%）。MemMachine（2026）则代表「拒绝写时压缩」的极端：原样保存全部 episode，把重活放在检索时，LongMemEvalS 达 93.0%，且比 Mem0 少约 80% 输入 token——说明**「写时压缩 vs 读时选择」是一个真实的权衡轴**（出处：[MemMachine 解析](https://effloow.com/articles/memmachine-ground-truth-agent-memory-paper-poc-2026)）。

### 4.6 三种范式的本质对比（全文核心）

| 范式 | 代表 | 上下文里剩下什么 | 信息可恢复？ | 成本发生在 |
|---|---|---|---|---|
| **有损压缩** | 摘要、LLMLingua、H2O | 更短的替代物 | ❌ 不可逆 | 写入时（一次性） |
| **无损搬运** | MemGPT 分页、Reference 指针 | 指针/占位符 | ✅ 原文可回取 | 读取时（按需） |
| **读时选择** | RAG、MemMachine | 每次现场挑选的相关子集 | ✅ | 每次请求 |

工程上成熟的系统是**混合**的：近期原文（无损）+ 中期摘要（有损）+ 远期向量/图谱（读时选择），三层之间靠指针衔接。这也正是 LlamaIndex「短期记忆 + 记忆块 + 向量库」的结构（出处：[LlamaIndex Memory 文档](https://llamaindex.openml.io/python/framework/module_guides/deploying/agents/memory/)）。

### 4.7 压缩问题的形式化（便于写代码）

设预算 B（token），候选单位集合 U，每个单位 i 有大小 t_i 和价值 v_i（重要性分）。目标：

```
max  Σ v_i · x_i          （保留的价值最大）
s.t. Σ t_i · x_i ≤ B，x_i ∈ {0,1}
```

这就是背包问题。实践用**贪心近似**：按 v_i / t_i（性价比）降序装入，直到预算耗尽——等价于「先压性价比最低的批」。若要求更优，可换 DP 或 LP 松弛，但贪心在消息管理场景已足够（单位数量小、价值分本身有噪声）。eBay 框架（arXiv:2603.29193）在此之上加了「连贯性感知」约束：被保留的单位集合必须在时间轴上连续或成段，避免上下文变成断章取义的拼贴。

### 4.8 压缩质量如何保障

1. **留验证集**：挑 50~100 条真实多轮对话，离线回放压缩管线，用「压缩后能否答对关于被压内容的问题」作为指标（LOCOMO / LongMemEval 基准的思路）。
2. **LLM 当裁判**：让强模型对比「全量上下文回答」与「压缩后回答」，评分一致性（LLMLingua 论文即采用此法）。
3. **监测信号**：上线后盯「用户重复提问率」「agent 回查指针的频率」，异常升高说明压过头了。
4. **保守原则**：压缩率分档渐进（先 2× 观察，再 4×），社区共识是过度压缩省下的 token 会被质量下降带来的重试吃回去。

## 五、端到端伪代码实现

```python
# ============ 1. 最小单位：工具调用组 ============
def unitize(messages):
    units, cur = [], []
    for m in messages:
        if m.role == "system":          # R1: 不进分批
            continue
        if m.role == "assistant" and m.tool_calls:
            if cur: units.append(cur)
            cur = [m]                   # 新工具调用组开始
        elif m.role == "tool":
            cur.append(m)               # R2: 并入当前组
        else:                           # user / 纯文本 assistant
            if cur: units.append(cur); cur = []
            units.append([m])           # R3: 轮边界
    if cur: units.append(cur)
    return units                        # -> List[List[Message]]

# ============ 2. 分批：token 主干 + 话题边界修正 ============
def batch(units, batch_token_budget=3000):
    batches, cur, cur_tok = [], [], 0
    for u in units:
        t = count_tokens(u)
        if cur and cur_tok + t > batch_token_budget:
            batches.append(cur); cur, cur_tok = [], 0
        cur.append(u); cur_tok += t
    if cur: batches.append(cur)
    return [Batch(units=b, tokens=sum(count_tokens(u) for u in b)) for b in batches]

# ============ 3. 预算控制器 ============
class BudgetController:
    def allocate(self, window):
        return {
            "system":      len(window.system),      # 固定，不动
            "tools_schema":len(window.tool_schemas),  # 固定或按需裁剪
            "output_reserve": 0.25 * window.total,   # 给输出留 25%
            "history":     window.total - 上述三项,   # 历史区的真实预算
        }

# ============ 4. 批处理管线（阈值触发） ============
def on_turn(window):
    budget = controller.allocate(window)
    if tokens(window.history) <= 0.7 * budget["history"]:
        return window                              # 未触发，直接发
    batches = batch(unitize(window.history))
    keep = []
    for b in oldest_first(batches):                # 从老到新处理
        if tokens(keep) + tokens(b) <= 0.7 * budget["history"]:
            keep.append(b); continue               # 还有空间，原样留
        op = decide(b)                             # 决策树：§3.5
        if   op == "DROP":      continue
        elif op == "SUMMARIZE": keep.append(summarize(b, merge_with=prev_summary))
        elif op == "EXTRACT":   memory_store.add(extract_facts(b)); keep.append(pointer(b))
        elif op == "EMBED":     vector_store.add(b); keep.append(pointer(b))
        elif op == "REPLACE":   keep.append(degrade_to_placeholder(b))
        # 若仍超预算 → 对 keep 里最早的一批再升一级处理（二次压缩）
    window.history = rerank(keep + recent_units, query=current_question)  # §3.4
    return window
```

`decide(b)` 的打分可直接复用 H2O 思想：维护每个批的累计相关性得分（被后续提问检索/命中的次数越多分越高），低分进 DROP，高分进 EXTRACT。

## 六、选型速查与常见陷阱

### 6.1 按场景速查

| 场景 | 最小单位 | 分批维度 | 主力算子 | 压缩范式 |
|---|---|---|---|---|
| 短对话机器人 | 消息 | 数量批 k=5~10 | 滑动窗口 DROP | 有损 |
| 工具型 Agent（Coding/DevOps） | **工具调用组** | token 批 3000 | REPLACE + EXTRACT | 混合 |
| 长会话客服/陪伴 | 工具调用组 | 语义批 + 时间批 | SUMMARIZE + EMBED | 有损+搬运 |
| 超长文档/数月记忆 | 话题段（episode） | 事件触发 | EXTRACT（事实+时间戳） | 读时选择为主 |
| 离线批量任务 | 请求 | 文件批 | —（走 Batch API 五折） | 不涉及 |

### 6.2 常见陷阱

1. **拆散工具调用组** → API 报错或模型幻觉。务必按 R1~R5 校验重装配后的结构合法性。
2. **摘要雪崩**：多层摘要合并再压，细节指数级丢失。对策：摘要带结构化字段（数字/承诺/待办），并限制压缩层级 ≤2。
3. **迷失在中间**：保留的内容若含关键中间消息，排布时把高相关的放开头或结尾（重排算子）。
4. **缓存失效**：压缩历史后前缀变化导致 Prompt Caching 命中率暴跌。对策：system + 长期事实放最前且保持稳定，变动历史放后面（[Anthropic 指南](https://hidekazu-konishi.com/entry/anthropic_claude_api_prompt_caching_and_token_efficiency.html) §4）。
5. **分词器错位**：预算按 tokenizer A 算、模型用 tokenizer B，限流失真。全程统一用目标模型的 tokenizer。
6. **写时压缩 vs 读时选择没想清楚**：高频回查的场景（如代码库问答）偏向无损搬运/读时选择（MemMachine 路线），低频回查才适合激进写时抽取（Mem0 路线）。
