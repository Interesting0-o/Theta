# 项目交接（project-handoff）

让接手的会话拿到**当前成果、有效决定和明确的第一步**，避免重复说明与两边同时修改。

> **铁律：提醒、保存、新建接续是三个不同动作，互不授权。** 提醒只建议、不落盘；保存只写
> 材料、不开新会话；用户确认了"保存并接续"才把三步连起来做。

## 1. 什么时候评估交接

只用已有任务事实逐条对照，三项**全占**才值得建议：

| 条件 | 判断依据 |
| --- | --- |
| 安全位置 | 当前操作已收拢，成果、验证状态、归属说得清；**用户尚未验收的不能写成已验收** |
| 明确后续 | 目标、范围、下一步与完成标准清楚——新会话看完材料就能确定第一步 |
| 切换收益 | 说得出这次切换的**具体**收益（如探索已结束、后面是纯执行）；"对话太长"不算收益 |

不提醒的情形：纯问答、任务没有后续、用户正在讨论本技能本身。

## 2. 怎么提醒

- **时机**：第 1 节评估通过、且你正要给出**最终答复**时。
- **位置与格式**：放在最终答复正文最前、单独一段，以"**交接建议：**"开头；写明具体原因、
  接续第一步、用户确认后你会做哪些动作。不放进引用块、示例或代码块。
- 例（仅格式示范，别当成项目事实）：

  交接建议：资料筛选已完成，后续进入方案编写，适合只带入选定资料与约束。确认后我会把材料
  写入 HANDOFF.md，然后你用 /new session 开新会话，我读它接着写方案。

- **去重**：同一阶段、同一个具体混淆只提醒一次；被婉拒后不因"又过了几轮"再提，除非出现
  新的实质阶段或新的已核实混淆。
- 用户回应"先不交接 / 继续做"：从回应起不再主动提，直到新的实质阶段；"做完 X 再提醒"以
  指定节点为准，到点再评估。用户说"本任务别再提醒"：彻底关闭主动提醒（显式要求交接仍执行）。
- **用户没有回应建议时：继续当前工作，不追问、不自动保存、不自动开新会话。**

## 3. 保存（用户明确要求时才做）

把材料整理成**一份** `HANDOFF.md` 写到**工作区根**（`create_file` / `write_file`，会过审批
——用户看得见写了什么）。已存在就整份覆盖重写：它是"当前任务态"的快照，不是追加日志。
结构：

1. **目标与范围**：这个任务在做什么、不做什么；
2. **当前成果**：做了什么、验证状态如何（跑过哪些测试/命令）；未验收的如实标"待验收"；
3. **有效决定**：已拍板的方案/口径/约束，以及为什么——避免新会话重新论证一遍；
4. **未决与坑**：还开着的问题、踩过的坑（环境、命令、依赖）；
5. **明确的第一步**：新会话读完就能照做的一个动作（命令或文件）；
6. **相关文件**：关键文件路径、分支名、运行方式。

写完回一句"已保存到 HANDOFF.md；接下来可用 /new session 接续"。

## 4. 接续与查看

- **接续**：新会话里系统上下文会出现"交接材料"指针（工作区根有 HANDOFF.md 时自动注入）——
  先 `read_file` 读它，核对无误再按"第一步"动工；发现材料与工作区现状矛盾时，**以现状为
  准**并向用户确认，不要照着过时材料继续跑。
- **查看**：用户只想看看 → 读出来讲，不顺手动工。

## 5. 与长期记忆的分工

- 长期记忆（`write_memory`）：**跨任务**的约束、偏好、项目事实（"这个仓库测试要用 -m pytest"）；
- 交接材料（`HANDOFF.md`）：**当前任务**的进度快照，任务终结后该被下一份覆盖或删掉。
- 别把任务进度写进 `write_memory`（污染跨会话记忆），也别把通用约束只写进 HANDOFF.md
  （会话一换就丢）。
